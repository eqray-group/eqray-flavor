## 晚上：order 模块主干（新建）

**提交**：`83e3297` 地基（表/枚举/错误码/试算引擎）→ `a3e86f5` 主干（服务/路由/前端）→ `be33823` 安全修正。

**表**：`cater_order` / `cater_order_item` / `cater_order_item_addon` / `cater_order_log` / `cater_cart`。表名用 `cater_` 前缀避开 SQL 保留字 `order`。

**锁定的口径**（改动前先读 AGENTS.md §4.11）
- 订单状态百位段位：100 待支付 / 200 待接单 / 300 制作中 / 400 待取餐 / 500 已完成 / 600 已取消 / 700 退款中 / 800 已退款。合法流转由 `enums.OrderStatus.CanTransit` 单点判定，对应测试设计 SM-00~07。
- `status`（订单状态机）与 `pay_status`（0 未支付 / 10 已支付 / 20 已退款）分离，不要合并。
- 计价是纯函数 `CalculatePricing(lines, rule)`，步骤顺序：原价 → 单品级 → 活动 → 券 → 积分（`07 §4` 唯一口径）。券门槛按活动后金额比较；整单优惠按行小计占比分摊，最后一行消尾差，保证「行应付之和 = 订单应付」。试算与下单共用 `resolveLines` 装配。
- 下单幂等靠 `(store_id, request_no)` 唯一索引兜底。
- 订单号即支付单 `merchant_order_id`；pay 加签回调到 `POST /api/v1/order/callbacks/pay`，订单侧验签 + 核对金额后推进状态。
- 超时关单顺序：**先关支付单（内部查渠道确认未收款），确认关闭后才取消订单**；渠道已收款则本轮不取消。禁止先取消订单再关支付单。
- 门店数据权限：管理端列表按可见门店过滤，详情与流转都校验归属门店；C 端会员只能看自己的订单。

**本次修掉的真实缺陷**
1. 行级（单品级）优惠没计入订单应付 —— 计价引擎补 `LineDiscountAmount`。
2. 必选加料组下限校验漏检：`groupMap` 只装「被选中的加料项所属的组」，必选组一个都没选就绕过了。改为按 SPU 加料组全集加载，且 `required=1` 时下限至少 1。
3. C 端下单让前端传 `channel`，传 `channel=2`（POS）可绕过「小程序渠道必须登录」的会员校验。改为控制器强制小程序渠道，请求结构删掉 `channel`。
4. 支付回调金额核对原来拿通知里的 `price` 比订单应付，改为「支付单金额 vs 订单应付」+「通知金额 vs 支付单金额」双重核对。

**新增能力**：`pay.PayOrderService.CloseByMerchantOrderID`（查渠道确认未收款再关单）、`PayOrderRepository.FindLatestByMerchantOrderID`、`CaterOrderRepository.BindPayOrder`、`param.QueryID`、`OrderService.DetailForUser`。

**前端**：管理后台 `views/order/index.vue` + 详情弹窗（金额拆分/明细含加料快照/状态日志），一键接单·出餐·完成·取消。
注意视图路径规范：菜单 component 必须写 `/模块/页面`（对应 `views/模块/页面/index.vue`），且页面路由名不能与目录重名（目录 path `/order` 会推出路由名 `Order`，页面改用 `OrderManage`）。

**规模**：order 模块 3.6 千行；全项目 app/ 下 44,379 行（不含测试）；迁移 114 文件 = 114 注册。

验证：go build / vet / test、vue-tsc、eslint 全通过；新增 `order_core_test.go` 9 组（状态机边界、终态判定、枚举取值、订单号格式、通知报文解析、优惠快照）。

## 晚间：promotion 模块落地 + 逆向补偿收口（提交 4bea786）

**产出**：`app/modules/promotion` 全套（enums / errs `1-007-*` / model / repository / service / 管理端 + C 端路由）、`order/service/order_promotion_service.go` 桥接层、前端 `views/promotion` 三个列表页与三个弹窗；迁移 `20261023000030`~`20261023000042` 共 13 个。

**核心设计（改之前先看 AGENTS.md §4.12）**
- 规则解析 `service/rule.go` 的 `Resolve` 是纯函数、不碰库；判定顺序固定按 `07 §5`。改玩法只动这个文件。
- 试算与下单共用 `order_promotion_service.go::buildPricingRule`，保证「试算价 = 下单价」，别在别处再装配一遍营销规则。
- 名额按 `(activity_id, period_key)` 计数，周期键整期 `fixed`、每日 `YYYY-MM-DD`；**占多少必须放多少**，靠 `promotion_order_activity` 记 `(order_id, activity_id, period_key)` 精确回退，不能按当前日期重算（跨天会退错池子）。
- 名额「用完跳过」而不是报错：规则引擎算价时就跳过名额满的活动，下单照常成功只是没优惠；占用环节报错只兜「算价时有名额、写入时被并发抢掉」这一竞态。

**注意 Goravel 坑（本轮又踩一次）**：`Where("id", "<>", v)` 同样是三参数，会编译成 `id IN ('<>', v)` 静默不命中。比较运算符（`< <= > >= <> != like`）一律写占位符 `Where("col op ?", v)`。

**修掉的既有缺陷**
- Goravel 三参数 `Where` 全库失效（15 处）
- `seed_member_levels` 误用表名 `member_levels`（表实为 `member_level`），等级种子从未落库 → `20261023000038`
- 订单状态列 `tinyint` 存不下百位段位 → `20261023000039` 改 `smallint`
- 上一个迁移漏改 `cater_order_log.from_status`，写日志溢出 → `20261023000042`

**端到端验证（项目内临时程序，验完已删）四场景全绿**：下单占名额→取消归零、支付结算→整单退款（积分/成长值/名额/券全部回滚）、名额占满时跳过活动、兑换比例 100→500 后仍按订单 `points_used` 出入。

**验证程序踩到的两个坑（下次写验证程序直接用）**
1. `datetime` 列不带小数位，用「此刻」当活动/券的开始时间会被取整到下一秒，导致刚建好就判定未生效 → 开始时间往前留 1 分钟。
2. 历次中断的运行会留下同名「验证活动」，规则引擎按优先级挑中旧活动，导致占错名额、查错计数行 → 建完本轮活动后先把历史验证活动停用（用占位符写法）。
