聚味云：多门店全渠道点餐系统

单品牌连锁的堂食 / 外卖 / 自提一体化平台。后端单体多模块，复用 eqray 框架的账号、会员、文件、短信能力， 自建门店、菜品、订单、营销、支付五个业务域。

代码库 eqray-flavor Go 1.25 · Goravel 1.18 · MySQL 8 · Redis Vue 3.5 · Vite 7 · Element Plus 评估日 2026-10-23

结论：地基扎实、设计成熟，但业务主干尚未贯通。 基础设施（认证 / 权限 / 会员 / 门店 / 菜品 / 支付）已落地 4.1 万行 Go 代码与 56 张表，分层纪律与编码规范执行得相当一致； 但订单、营销、库存、KDS、结算、打印任务六个域零代码，而订单正是全系统最复杂、耦合最深的部分。

更需要留意的是：进度文档已经落后于代码。支付模块在 10-22 被整体重写为支付中心（12 张表，对齐 yudao）， 但两份进度文档仍在描述旧的「精简版」；AGENTS.md 至今没有收录 dish / pay 模块。 任何按文档接手的人都会误判项目规模 —— 这是当前投入产出比最高的待修项。

01产品定位与形态

一句话：账号、会员、文件、短信用现成的；门店、菜品、订单、营销、支付按同一套规范自己造。

维度设计
业务模式单品牌连锁：1 个总部（可设大区）→ N 家门店（直营 / 加盟）。门店是经营单元，总部是菜品与价格的唯一真相源
渠道扫码堂食、外卖配送、到店自提，三渠道汇入统一订单中心
终端管理后台（内含 POS / KDS 路由）、顾客端小程序、骑手端、商户端；当前仅管理后台落地
形态选择拒绝微服务：一个二进制、一个端口、模块间包调用。单品牌门店量级下，运维成本与本地事务一致性优先于弹性扩容
核心矛盾「会员 / 券 / 钱包刻意不带门店维度」= 跨店通用；「订单 / 桌台 / 库存必须带门店」= 严格隔离。这条线是全系统数据设计的骨架

02架构与依赖纪律

依赖铁律只有两条，但执行得干净：只允许上层依赖下层；跨模块只调 Service，禁止读别人的表。

业务层
store 门店 dish 菜品 pay 支付 order 订单 promotion 营销
↓ 只调 Service
通用层

↓
基础层
base 认证 / 响应 / 错误码 / 中间件

一次请求的链路

1全局日志中间件记录访问信息，不阻塞响应
2TokenAuth 校验令牌：后台写登录者身份、C 端写会员身份，两套令牌互不通用
3后台再过权限点（模块:资源:动作，超管直接放行）；C 端只看会员身份，不参与 RBAC
4门店级请求先过 X-Store-Id 中间件：校验门店存在、是门店类型、在当前用户可见范围内，才写入上下文
5Controller 取参 → Service 业务 → Repository 查询；统一返回 {code, msg, data}，HTTP 恒 200

04值得肯定的设计决策

这批决策比多数同规模项目清醒，直接决定了后续开发的返工量。

决策为什么重要
状态与钱分离status 只表达业务进度，pay_status 只表达收款。避免「已支付 / 已退款」混进订单状态机，导致非法流转与报表口径混乱
堂食先做后付堂食下单不建支付单、直接进后厨，结账才收款。这决定了订单不能假设「一单对应一笔支付」，也因此必须支持分次结账 —— 设计在早期就把这条打通了
金额只信服务端价格、优惠、积分全在服务端试算，客户端只做展示；支付金额与应付不一致直接拒绝。资金安全的第一道闸
优惠计算唯一口径原价 → 单品级 → 商品级活动 → 订单级活动 → 券 → 积分 → 储值，七步写死在一个文档里。营销最怕「试算与结算两套算法」，这里从设计上堵住
门店上下文 + 可见范围缓存X-Store-Id 统一入口校验；可见门店集合缓存 30 分钟，员工变更主动失效；没有员工关联视为总部全量账号。越权面被收敛到一个中间件里
条件更新代替「先查再改」骑手抢单、桌台开台清台、券状态流转都用 WHERE 状态=旧值 的原子更新，并发下不会超接、不会重复核销。这是订单期最需要复用的模式
打印模板带版本与快照模板正文变更自动递增版本，历史打印任务保存渲染快照。换机补打的内容与首次一致，不会因为改了模板就对不上账
支付与业务解耦支付回调不直接改业务单，而是写 pay_notify_task，由定时任务加签推送给业务方。业务侧可重试、可补偿，订单不必理解渠道细节

05文档与代码的偏差

这是本次研究最需要汇报的部分。共发现 7 处，前 4 处会实际误导判断或引入 bug。

1. 支付模块已被整体重写，文档仍在描述旧版高

docs/design/22 写的是「精简版：只保留 pay_order / pay_refund 两张表，全平台一个收款账户，参数读 config/pay.go」。 实际代码里已是完整支付中心：pay_app、pay_channel、pay_order、pay_order_extension、pay_refund、 pay_notify_task、pay_notify_log、pay_transfer、pay_wallet 及三张钱包表，共 12 张，渠道从数据库读而不再读环境变量。 迁移 20261022000060_drop_pay_tables_before_yudao 就是这次重写的分界点。

2. 两份进度文档互相矛盾高

design/22 说 dish / pay 已完成大半；docs/开发任务.md §七 仍记「M3 支付 0 完成、6 个未开始」，合计 10 完成 / 43 未开始。 两份文档都自称权威（22 说自己是「进度单一事实源」，任务文档说自己是「任务拆解」），但没有同步机制，谁也没更新对方。

3. AGENTS.md 未收录新模块高

根目录 AGENTS.md 294 行，模块表里只有 system / infra / member / store，全篇没有出现 dish、pay、order 字样。 这是给 AI 助手和新人看的入口文件 —— 按它接手，会认为菜品和支付不存在，甚至可能重复造一遍。

4. config/pay.go 已是半死配置中

文件里 wechat.*、alipay.*、expire_minutes 现在无人读取，仅剩 notify_base_url 还在用（回调地址拼接）。 但注释仍写着「全平台共用一个收款账户」，与实际「多应用多渠道、配置存 pay_channel.config」完全相反。留着的风险是：有人照着它去配 .env，配完发现不生效。

5. 迁移记录比文件多 14 条中

运行日志显示数据库 migrations 表已执行 116 条，而仓库迁移文件只有 102 个。 差额来自历史删改文件但未清理记录，属于 AGENTS.md 已警示过的坑。后果：新环境从零迁移与现网结构可能不一致，需要比对一次。

6. 数据字典表与代码枚举不同值中

design/12 把 pay_channel_code 写成「公众号 / 小程序 / 支付宝 / 余额」，代码枚举实际是 wx_pub / wx_lite / alipay_* / wallet。 另外支付模块的开启状态沿用 yudao 口径「0 开启 / 1 关闭」，与全站 common_status「1 启用 / 0 禁用」相反 —— 这条只在代码注释里，没有进文档，是很容易踩的反向逻辑。

7. 数据模型文档缺 4 张支付表低

design/03 §8 支付域只列了渠道 / 支付单 / 退款 / 通知 / 钱包 / 充值，缺 pay_app、pay_order_extension、pay_notify_log、pay_transfer。

06风险清单

按「会不会挡住上线」排序，而不是按工作量。

订单域 0 行代码，却承担最复杂逻辑 阻塞

试算、同桌合并、分次结账、加菜退菜、幂等下单全压在这一个模块。设计文档给了口径，但没有一行代码验证过这些规则能否落地。M4 是 9 个任务，实际工作量可能超过已完成的全部模块之和。

支付无任何单元测试 阻塞

现有 8 个测试文件全在 store 与 dish，pay 的 service 目录 no test files。回调验签、AES-GCM 解密、金额一致性校验、退款超额拦截，这些「错了就赔钱」的分支没有任何自动化保护。

dish 与 pay 全部未提交 阻塞

git status 显示两个模块、22 个迁移、pay 配置全是 untracked，仓库只有一个 store 提交。这是近 2 万行代码裸奔在磁盘上，一次误操作就没了。

真实商户号未联调 高

微信 / 支付宝只完成代码侧签名与回调处理，没有真实商户号跑过一笔。证书、平台证书序列号、回调地址可达性、验签失败的具体表现都还是未知。

无并发验证的库存与名额 高

设计要求「缓存原子预扣 + 数据库条件扣减」，但目前既无库存表也无名额表。限量 10 件 50 并发只成功 10 单，这个用例还没有代码可测。

前端只有管理后台 高

POS、KDS、顾客端小程序、骑手端四个终端全是空目录。系统「能配」但顾客「不能点」，这是从 demo 到可用之间最大的一道鸿沟。

定时任务多实例安全 中

三个任务都加了 OnOneServer()，这点做得对。但订单期还要新增超时关单、券过期、库存校准等一批任务，需要统一按此模式落地，别漏。

单库单表的天花板 中

设计明确「一期单库，订单到百万级再按门店分表」。以连锁餐饮的订单增速，这个阈值大约在 12~18 个月内到达，需要提前准备归档策略而非临时改表。

07建议的推进顺序

先止血，再攻坚。前两步各半天到一天，收益远大于继续写新功能。

提交现有代码，清理文档漂移

先把 dish / pay 提交入库；改 design/22 的支付描述、开发任务.md §七 的 M3 计数；AGENTS.md 补 dish / pay 两个模块段落；删掉 config/pay.go 里已死的渠道配置，只留 notify_base_url。

理由：近 2 万行未提交代码是最高风险，而文档偏差会让每个接手者重新踩一遍同样的坑。

给支付补最小测试集

四个用例就够挡住大部分事故：重复回调只置一次已支付、回调金额与支付单不符必须拒绝、退款金额超过可退额必须拒绝、钱包扣减并发不出现负余额。

理由：支付是唯一「错了直接损失钱」的模块，也是目前唯一零测试的核心模块。

订单域按「建表 → 试算 → 下单幂等 → 状态机」四步走

对应 T-ORDER-01 到 04。建议把试算做成纯函数（输入明细 + 会员 + 券，输出金额与步骤明细），先离线跑通设计文档 13 里的 AM-01~AM-08 用例，再接数据库。试算是最容易出错也最容易单测的部分，先把它焊死。

理由：试算是订单的地基，且与支付、库存解耦，可以独立验收。

再接支付回调，打通堂食与外卖两条闭环

堂食走「下单即制作 → 结账收款」，外卖走「下单 → 支付 → 接单」。两条链路各跑通一单真实数据，比写十个接口更能暴露设计漏洞。

理由：设计要求堂食不建支付单，这条差异只有在真实闭环里才会暴露边界问题。

出餐单与 KDS 紧随订单，不要提前做营销

KDS 依赖出餐单，出餐单依赖订单；打印任务又依赖出餐单。营销虽然诱人，但它是订单试算的下游，先做会因为没有订单数据而反复返工。

理由：现有任务路线（M5 出餐 → M6 营销）顺序是对的，不要因为营销「看起来简单」而插队。

顾客端小程序与订单并行推进

管理后台已经能配门店、配菜品、配渠道，但顾客无法下单，整套系统就没有验证场景。建议在订单接口稳定后立即启动小程序，用真实扫码流程反向压测订单设计。

理由：这是唯一能让前 4 万行代码产生实际价值的路径。

08一句话总结

做得好的分层纪律、状态机设计、金额口径、门店数据隔离、支付与业务解耦 —— 这五项在同行项目里属于上游水平，而且是真的落到代码里了
最大的问题不是技术，而是信息同步：代码跑得比文档快了一个版本，导致「项目到底做到哪」这个问题有三份互相矛盾的答案
最大的未知订单域。设计写得越细，落地时的偏差越需要验证；建议把试算与状态机当成两个独立可验收的里程碑，而不是一个大任务
成熟度判断基础设施可投产，业务链路约完成三成。距离「一家门店能用它跑完一天营业」还有 M4~M7 四个阶段
