# 24 · 自配送与骑手设计

> 上一份：[23 管理端对接约定](./23-store模块接口与前端对接.md)｜返回：[文档总览](./README.md)

**一句话**：外卖由商家自有骑手配送，先做「门店开关 + 范围校验 + 抢单」，不做派单算法。
**状态**：store 已落地门店表、组织树、`delivery_enabled` 外卖开关与骑手档案；配送单、抢单 HTTP 接口与订单校验尚未实现，本文只定规则。

---

## 1. 门店侧开关

| 能力 | 配置 | 默认 |
| --- | --- | --- |
| 堂食 | 无 | 开 |
| 自提 | 无 | 开 |
| 外卖 | 门店开关 `store.delivery_enabled` | **关**，需单独开启 |

- 顾客端按开关决定是否展示「外卖」入口，关闭时顾客选不到，而不是下单才报错。
- `online_enabled` 是线上总开关（堂食/自提/外卖），`delivery_enabled` 只控制外卖入口；二者独立，外卖关闭不影响堂食与自提。
- 后厨不设「档口」层级：门店直接对应后厨打印机，菜品不再分档口。

---

## 2. 配送规则

规则随门店保存，包含：配送半径、起送价、配送费、每份打包费、预计送达时长。

**保存时校验**：

1. 规则格式非法 → 拒绝保存；
2. 金额、时长为负 → 拒绝；
3. 半径为负数 → 拒绝；填 0 或不填表示不限范围（JSON 结构见 [03 §4](./03-数据模型设计.md)）；
4. 开启外卖但未配规则 → 允许保存，下单时按「不限范围、费用为 0」处理并记警告日志。

> 不能把「必须配齐」做成运营改门店的阻塞，但必须在日志里暴露问题。

---

## 3. 下单校验

外卖单按固定顺序校验，试算与下单共用同一套逻辑：

1. 门店是否开启外卖；
2. 收货人、电话、地址、坐标是否齐全；
3. 是否达到起送价；
4. 是否在配送范围内（直线距离）；
5. 计算应付：商品小计 + 配送费 + 打包费。

补充规则：

- 门店未配置坐标时跳过范围校验，并记警告。
- 收货坐标缺失在第 2 步拦下。
- 直线距离不等于实际路程，一期够用；需要精确再接地图路径规划。
- 收货信息落库时保留快照，供纠纷举证。

---

## 4. 配送单

**状态**：待接单 → 已接单 → 配送中 → 已送达；任意进行中状态可转已取消。

- 只有「待接单 → 已接单」允许抢占，其余按序推进，不允许跳状态或回退。
- 一张订单只生成一张配送单，重复下单不会重复生成。
- 配送单号由骑手端与电话沟通使用，需可读且唯一。

**关键信息**：骑手（空表示待接单或商家自送）、直线距离快照、预计时长快照、
金额冗余（商品、配送费、应付）、收货信息冗余、接单 / 取货 / 送达三个时间点。

> 金额、时效、地址冗余到配送单，是为了骑手端不依赖订单表；快照保证门店事后改规则不影响已下单。

---

## 5. 骑手

骑手由三部分组成：

| 组成 | 作用 |
| --- | --- |
| 后台账号 | 骑手登录，账号即手机号 |
| 门店员工关联 | 决定骑手可见门店（数据权限来源） |
| 骑手档案 | 接单状态、并发上限、今日单量 |

- 骑手归属**后台账号体系**，不是会员。
- 新建骑手时若未指定账号，自动创建后台账号并挂门店员工；初始密码只在创建响应返回一次。

**状态**：空闲 / 接单中 / 配送中 / 休息 / 停用，与 [12](./12-枚举与数据字典总表.md) 的 `store_rider_status` 一致；「接单中」指可抢单的在线态，不是配送单的待接单。停用不影响历史记录。

**并发安全**：接单用条件更新抢占（状态匹配 + 未超并发上限），送达后释放名额；
不允许「先查再改」，否则会超接。商家可指派、可代确认送达，用于骑手失联兜底。

**已实现口径**

- 表 `store_rider`：`employee_id` 唯一，`store_id` 与员工归属门店一致；`max_orders`
  默认 3、范围 1 ~ 20；`current_orders` 记录进行中配送单数；`today_orders` 配合
  `stat_date` 在跨日首次接单时重置。
- 状态 `1` 空闲 / `2` 接单中 / `3` 配送中 / `4` 休息 / `5` 停用；只有 `2` 且
  `current_orders < max_orders` 能通过条件更新抢单。休息 / 停用时必须没有进行中订单，
  并发上限不能低于当前负载；后台编辑与删除同样使用条件更新，避免校验后被并发接单插入。
- 停用骑手会同步禁用门店员工；删除骑手采用软删除并禁用员工，历史档案保留。重新绑定
  同一员工时恢复原档案并重置负载，后台账号不删除。
- 未指定后台账号时通过 `support.AccountProvisioner` 自动创建：手机号为账号、姓名为昵称，
  12 位随机初始密码只在创建响应返回一次，库中只存 bcrypt 哈希。
- 自动开通的骑手账号不分配 system 角色；骑手端接口按门店员工与骑手档案鉴权，不依赖 RBAC
  菜单权限。
- 管理端页面 `src/views/store/rider/index.vue`，路由名 `StoreRider`，权限点
  `store:rider:list/create/update/delete`。`TryAccept` / `Release` 目前只在服务层提供，
  等配送单模块接入 HTTP 路由。

## 6. 抢单

一期只做抢单，先到先得：

1. 外卖支付成功后生成配送单，状态待接单；
2. 骑手端展示本门店待接单单据，按距离升序，限制单次数量；
3. 骑手接单成功后写轨迹；失败说明已被抢。

骑手端优先用推送，轮询兜底。手上有单时不允许下线，避免配送单悬空。
当前骑手服务已提供 `TryAccept`（条件更新抢单）与 `Release`（幂等释放名额），等配送单
模块落地后直接调用，不新增第二套抢占逻辑。

---

## 7. 配送轨迹

只追加不修改，每次状态流转写一条：配送单、原状态与新状态、操作方类型与操作人、
位置描述、备注。

用途：纠纷举证、骑手申诉、超时定责。一期只提供查询，不做前端页面。

---

## 8. 订单与配送联动

| 订单事件 | 配送动作 |
| --- | --- |
| 外卖支付成功 | 生成配送单并写轨迹 |
| 订单取消 / 超时关单 | 取消配送单，释放骑手名额 |
| 订单退款 | 取消配送单，避免继续配送 |
| 骑手送达 | 释放名额，骑手回空闲 |

- 配送是**辅助流程**：生成或取消失败只记日志，不回滚收款、不影响订单状态。
- 异常由管理端补单处理；订单状态始终是权威。

---

## 9. 超时兜底（未实现）

| 场景 | 处理 |
| --- | --- |
| 长时间无人接单 | 扫描待接单超时，提醒商家 |
| 接单后长期未取货 | 扫描已接单超时，提醒商家 |
| 超预计送达时长 | 对比取货时间与时效，标记超时 |
| 骑手失联 | 商家重新指派或代确认送达 |
| 配送与订单状态不一致 | 定时对账 |

---

## 10. 已知取舍

1. 骑手复用后台账号，不新建账号体系；代价是骑手端接口与后台同前缀。
2. 用直线距离判断范围，不接地图路径规划，误差几百米。
3. 抢单制，不做派单算法。
4. 固定配送费，不做距离阶梯。
5. 不做第三方外卖平台对接，另见 [16](./16-外卖平台对接设计.md)。
6. 超时不自动取消，只统计与提醒，避免误杀正在赶来的骑手。
7. 骑手收入与结算不在本期，等结算方案确定。
8. 骑手档案删除是软删除，员工关联与后台账号保留；停用 / 删除前必须保证没有进行中配送单。
